# McGod project handoff — 2026-09-07

This is the current operational snapshot of McGod. It supersedes the phase status and
"next" sections in `CLAUDE.md`; that file remains useful as architectural history and for
the reasoning behind earlier decisions. `SESSION-2026-09-04.md` is the detailed development
log for the work that led here.

The project is working end to end. Its goal is a Minecraft god that knows the player's lived
history and the current world accurately, speaks about both in natural in-world language, and
can inspect uncertain evidence instead of inventing an answer. The highest-priority quality
bar is coherent current-world representation, especially player-built structure segmentation,
naming, rendering, identity, and upkeep.

## Current status at a glance

- Paper 26.2 captures gameplay into durable JSONL and a live WebSocket bridge.
- The Python agent replays all recorded evidence into SQLite at startup, then consumes live
  events through the same indexing path.
- Historical questions use one general pipeline: the dialogue model writes bounded read-only
  SQL, chooses any additional world tools it needs, and narrates the evidence in plain speech.
- Current player builds, historical work, vanilla/generated places, and terrain knowledge are
  separate concepts and separate tables.
- Current structures are segmented from live voxels, not reconstructed from placement sessions.
- Structure interpretation has dedicated vision routing. In the current OpenRouter setup,
  Luna handles dialogue/general classification and Gemini 3.7 Flash handles images.
- Both smiley faces and the golden arch are current player-built structures. The arch was
  migrated out of generated-world storage after exact block history proved its authorship.
- All 294 Python regression tests pass. The plugin builds successfully.
- Every built mass in read ground is on a deterministic ledger (`masses`), whatever its
  size or author; named structures are groupings of those masses.
- The render audit passes with 11 canonical player structures and one review sheet per object.

## Non-negotiable design rules

These are product requirements, not temporary implementation preferences.

1. The world is the authority for what exists now. Events say what happened and where to
   inspect; they are not a permanent voxel model.
2. Preserve the complete low-level action ledger. Do not replace it with lossy recency
   summaries. Retrieve by relevance, time, place, actor, vehicle, and other evidence.
3. All historical questions take the same route: model interprets the question, model writes
   read-only SQL, model may call other evidence tools, model narrates the results. Do not add
   exact-phrase gates, special query templates, or deterministic prose shortcuts.
4. Generated-world places are never player builds merely because the player visited, looted,
   or edited them. A generated building may carry player modification history without changing
   authorship. A genuinely new player object inside a village remains player-built.
5. Do not special-case one structure, material, shape, phrase, or screenshot. Fix the general
   representation, evidence contract, model instruction, or deterministic invariant.
6. The model proposes semantic judgments; code enforces factual and safety boundaries. Code
   validates bounds, read-only SQL, provenance, identity, render publication, and quest state.
7. Geometry and naming are separate beliefs. A scan can establish extent without proving what
   an object means.
8. Something the god said is never evidence that it is true. `ASSERTED` provenance cannot be
   promoted into world fact.
9. Coordinates, UUIDs, SQL, telemetry, and database terms are internal evidence. God speech
   should use landmarks and cardinal descriptions unless the player asks for coordinates.
10. Do not announce irrelevant policies in dialogue. Simply avoid raw coordinates; do not say
    that coordinates are being withheld.
11. A missing observation is not proof of absence. This matters for old sessions, unloaded
    chunks, failed scans, stale entity counts, and event types added after the first recordings.
12. Every general fix should gain a replayable regression or evaluation case where practical.

## End-to-end data flow

```text
Paper events
    │
    ▼
bounded main-thread queue ──► JSONL session files
    │
    ▼
one durable WebSocket connection
    │
    ├──► live ingestion ──► event_history + deterministic indexes
    │
    └──► bounded RPC: scans, voxels/renders, seed environment, speech
                                      │
                                      ▼
                              SQLite belief/world store
                                      │
                       ┌──────────────┴──────────────┐
                       ▼                             ▼
              chat evidence loop             dirty-region upkeep
              SQL/tools/narration             scan/segment/publish
```

The plugin stays simple and fast. Bukkit/Paper state is read on the main thread, events are
enqueued, and serialization/network work happens off-thread. A full queue drops events instead
of stalling the server. Live consumption and replay share the same downstream consumer contract,
so recorded sessions are the development fixture.

At startup, `sync_world()` finds corpus and server JSONL files, deduplicates copies by content
identity, and rebuilds deterministic layers. It records permanent history, activities, episodes,
work events, player state, and dirty regions before applying structure-origin and generated-
hierarchy migrations. Live events then extend the same store.

## The world-state model

The most important separation is current state versus history versus generator knowledge.

| Store | Meaning | Mutability/authority |
|---|---|---|
| `event_history` | Lossless observed gameplay events with full JSON payload | Permanent; never decayed away |
| `activities` | Search-friendly interpreted deed index | Rebuildable from event history |
| `episodes` | Deterministic time/space activity aggregates | Rebuildable |
| `work_events` | Immutable historical placement/removal footprints | History, not proof an object remains |
| `masses` | Every connected built mass in read ground, any size, any author: geometry, materials, footing, levels, builders, edit history, `place_id` | SCANNED; rewritten by every read; retired only by measured absence |
| `structures` | Canonical current player-built spatial objects, each a named grouping of masses (`comprises`) | Updated by fresh voxel segmentation |
| `generated_features` | Seed sites and scanned vanilla components | Generator-authored and disjoint from builds |
| `terrain_regions` | Cached seed-backed biome samples | High-level environmental evidence |
| `relationships` | Names, containment, modification, and semantics | Each relation has provenance |
| `players` / `actor_presence` | Player summary and generated-place membership | Replaceable observed state |
| `quests` / `watchers` | Persistent intent and cheap completion state | Explicit lifecycle |
| the seed map | Generation itself, computed on demand and never stored | Not a table: `seedmap.py` computes it from the seed |
| `regions` | Visited dirty-region reconciliation queue | Work queue, not a complete world map |

Every belief row carries confidence, provenance, first-seen time, verification time, and source
event IDs. Provenance order is:

| Provenance | Source | May be spoken as fact? |
|---|---|---|
| `SCANNED` | direct world read | yes |
| `OBSERVED` | captured event or explicit human observation | yes |
| `DERIVED` | deterministic computation | yes |
| `INFERRED` | model judgment | only above the configured threshold |
| `ASSERTED` | prior god speech | never |

Confidence decay happens at read time and is fact-specific. Entity occupancy decays quickly;
structure geometry and names decay much more slowly. The stored observation is not rewritten
merely because time passed.

### Authorship and generated-world separation

Location and current material cannot determine authorship. Player-build attribution replays
exact block mutations per coordinate and compares the latest mutation with the material that
exists now. A majority of supported current blocks establishes player authorship. Being near
or inside a village is not an authorship feature.

Existing generator identities remain generated when renovated. Their modifications are linked
to the player through work history and relationships. Conversely, a distinct new build erected
inside a generated settlement belongs in `structures`.

Startup reconciliation repairs legacy rows previously classified from location. It atomically
moves the object, its name/relationships, and its render between ontologies. This migration
moved the golden arch from generated storage to player-built storage.

## Structure segmentation, identity, and upkeep

Two tiers, added 2026-09-07 (see `SESSION-2026-09-07.md`). The **ledger** (`masses`) is
deterministic and complete: every connected mass of built blocks in read ground is a row,
including pillars, bridges, scaffolds, torch lines and generated buildings, with builder shares
replayed from exact block history, first/last edit times, edit counts, footing and per-level
occupancy. Natural-material blocks count as built when history proves a player placed them.
The **landmark** tier (`structures`) is the model-curated set of named things, each anchored to
the masses it comprises. The model decides what deserves a name; it no longer decides what
exists. Unnamed masses at or above eight blocks carry an INFERRED `role` belief from a cheap
text call over facts alone.

Segmentation is spatial and current-world based:

1. Gameplay disturbance marks a region dirty.
2. After activity settles, the agent scans a bounded live voxel patch.
3. Code writes the ledger for that patch: masses measured, attributed, matched to prior ids.
   A mass cut by the read edge is `partial`, never overwrites a whole record, and queues a
   look past that face into occupied ground only.
4. The vision model proposes meaningful object boxes and names from rendered and
   coordinate-bearing evidence, and is shown the measured masses as exact geometry.
5. Code clips and measures proposals, rejects empty or scan-edge partial boxes, enforces a
   universal minimum of eight occupied blocks, and performs a focused second look.
6. Existing IDs are matched one-to-one using geometry and material similarity, not names.
7. The replacement set is committed atomically; only direct evidence can retire an object.
   Masses are re-anchored to the new landmarks, history rows in the window are relinked to
   the mass or landmark they happened in, and unnamed masses are asked about.
8. Canonical renders are published after the database commit.

The minimum size is universal. There are no exemptions for smileys, gold, statues, rails, or
particular shapes. The model decides whether a small grouping is meaningful; code only applies
general measurement rules.

Segmentation input includes exact occupied-height slices and a clean structural view. Natural
terrain is suppressed in slice grids so sparse builds are not drowned in grass noise. Objects
are cropped and shown through rotations. Existing semantic names/descriptions are withheld from
the first pass to prevent anchoring.

The second look is view-aware:

- horizontal planar work gets a labeled top view;
- upright planar work gets the most informative front or side elevation;
- volumetric work gets all four views.

This pass can revise the initial name. Stronger observed human naming cannot be overwritten by
later inference. If a weaker proposed name is rejected, the render filename still uses the
canonical stored name.

Splitting a rail station or shelter from a long track segment is acceptable and often desirable
for complex worlds. Identity should reflect separable objects, not force every connected block
network into one structure.

### Canonical rendering

The renderer uses Minecraft client textures and block models. Each sheet is a 2x2 layout:

- upper-left: perspective;
- upper-right: true orthographic top view;
- lower-left: front elevation;
- lower-right: side elevation.

All views use the same geometry pipeline. The top view is not a heightmap shortcut. Structure
sheets omit entities because entity models previously obscured and distorted the object. When
occupancy matters, the model can call a separate exact entity census for the requested bounds.

The model also has `render_world_area` as an ordinary evidence tool. It should use a fresh
bounded render for visual judgments—especially “what did I build?”, resemblance, appearance,
and modifications—instead of relying on block counts or an old label. A current render cannot
prove historical appearance, so it must be combined with the event interval.

`agent/renders/` is a materialized review view. Top-level PNGs correspond one-to-one with current
player structures. Generated component sheets live under `agent/renders/generated/`; excavations
and environment evidence have their own subfolders; stale sheets move to timestamped archives.

## Historical question pipeline

There is exactly one production path for historical questions in `history.py`:

```text
player text
  -> dialogue model decides whether it is historical
  -> model writes one or more tailored read-only SQL queries
  -> bounded SQLite execution returns evidence
  -> model may query seed information, render the world, or inspect entities
  -> the same model interprets the evidence and returns plain speech
```

Enumerating what stands somewhere is the one shape that does not come from the ledger of
actions: it is the structures in that area plus the masses there with a null `place_id`, two
disjoint sets that together are everything built. Block placements are history and include
what was later removed, so reading both names the same thing twice.

Historical answers must retrieve `event_history`; summaries are optional indexes, not the
authority. The model may join or follow results through `structures`, `generated_features`,
`relationships`, `terrain_regions`, `activities`, `episodes`, `work_events`, `players`, and
`actor_presence`. It receives up to six tool rounds so results can reveal a place, vehicle,
time interval, or render bounds needed by the next query.

SQL is restricted to an allowlist, `SELECT`/CTE statements, 1,500 returned rows, a 300,000-
character result budget, and a SQLite instruction budget. Mutation, pragmas, attachment, and
schema operations are denied by the authorizer.

Important evidence semantics include:

- search all recorded time unless the player's wording imposes a range;
- `container_open` proves looking, not taking; container diffs prove net movement;
- a container event carries the container's own coordinates, so taking from a chest the
  player placed is not theft; material payloads carry their namespace and block state, and
  comparing against a bare name returns an empty set rather than an error;
- only `villager_trade` proves a trade;
- damage proves combat, while only `mob_kill` proves a kill;
- only a successful sleep result proves sleep;
- passenger events or occupancy snapshots can connect a mob and player ride;
- captured surface state, not biome inference alone, distinguishes land from water;
- resolve place IDs into player or generated structure evidence;
- merge low-level events into supported human deeds without inventing gaps.

A request to act is never historical, however it is phrased: "give me a sword" wants the
sword, not an account of whether one was ever given. The evidence loop steps aside without
looking anything up, and the dialogue path acts. What someone has built or done stays
historical however local the question.

The trivial greeting path returns a short greeting. Every other message first gets semantic
historical inspection; non-historical input proceeds to current grounding, quest, advice, or
general dialogue.

## Seed and unvisited-world knowledge

There are two sources, and they answer different questions.

The plugin's **environment service** asks the running generator. It inspects high-level biome
samples and locates the nearest of selected vanilla structures, including places the player has
not explored. It is authoritative and needs the server up.

The **seed map** (`agent/seedmap.py`) computes generation directly from the seed, offline, using
vendored cubiomes patched to 26.2 (`agent/cubiomes/`, MIT; see its `PROVENANCE.md`). It is the
only source that can answer how MANY of something exist over an area, or list them all, rather
than where the nearest one is. A ten-thousand-block village count takes about ten milliseconds.

It also searches far past the plugin's range. `query_seed_map` covers structures (nearest, all,
count), the biome at a point, the nearest patch of a named biome, the biome distribution over an
area, world spawn and strongholds. "Nothing within 4,096 blocks" from the server-backed tool is a
reason to ask the seed map, not an answer: the nearest ice spikes on the test world is 6,233
blocks out, and the server confirms it.

Results are linked back to what the god already knows: a computed position that coincides with a
generated site on record carries that site's identity, and the one the player is standing in is
marked. Without that, "the closest village other than the one I'm in" was answered with the
village they were standing in.

It exists because the god answered "how many villages are within 10,000 blocks" with 8, by
counting rows in `generated_features`: five sites it had located plus three component buildings
of one of them. The real answer is 272.

Both are exposed to the dialogue model as evidence tools. The evidence loop in `history.py` now
answers world questions as well as historical ones; a historical claim must still retrieve
`event_history`, and a world claim must retrieve seed or environment evidence.

Three limits, carried in every seed-map result so the model can hedge:

- It describes the world **as generated**, never as it stands. It does not know what anyone has
  built, mined, looted or destroyed.
- Placement is exact; the terrain check that decides whether a candidate becomes real is exact
  for most types and approximate for a few. `seedmap.ACCURACY` records which, measured against
  the running server, and an approximate result says so and asks to be confirmed.
- It is exact for the version it was built for. `seedmap_truth.json` pins known answers so a
  version bump or a library change fails the regression suite rather than quietly describing a
  different world.

Seed knowledge remains high-level either way. It does not establish current fine-grained blocks,
container contents, edits, exact travel surface, or entity occupancy. Those require events or a
live scan.

## Event capture contract

Every event has ordered core fields `tick`, `t`, `type`, `actor`, `dim`, and `pos`, followed by
type-specific fields. Existing meanings are frozen; additions use a new type or optional fields
so old sessions stay replayable.

Captured categories include:

- block placement/breaking, explosions, signs, portals, weather, and dimensions;
- movement, region entry, periodic player state, join/quit, respawn, and death;
- pickups, drops, crafting with ingredients, smelting, enchanting, container diffs, trades,
  eating, XP, and item breakage;
- damage dealt/received, kills, potion effects, breeding, taming, shearing, fishing,
  projectiles, and advancements;
- `mob_death`: a death the player did not cause, carrying victim, killer (followed back
  through a projectile), cause, custom name and tamed flag. Kept when another entity killed
  it, or when the victim was not a monster; a zombie burning at sunrise is not recorded.
  Its actor is `world`, so it is never one of the player's deeds;
- bed attempts including failure result;
- player and non-player vehicle enter/exit, stable vehicle/passenger IDs, occupant snapshots,
  water state, and sampled surface material;
- chat and player commands.

Movement is sampled every two seconds, pickups roll up per item type over one minute, and heavy
player state is sampled every ten seconds. Current defaults are a 65,536-event queue, one-second
sink flush, four scan chunks per tick, and loopback bridge `127.0.0.1:8765`.

Do not reintroduce generic player-interact capture; it is too noisy. Do not reintroduce a
separate block-modify event for farmland or paths; Paper reports those as block placements and
the duplicate event previously corrupted the stream.

## Answer latency

Speech has its own queue and worker. Chat drained from the same queue as every other event
behind a single worker, so a question waited on whatever the loop was already doing, which
after a quest completion is renders and model calls. Every renderer call in the live loop runs
in a thread; a test fails on any that does not.


Every model call has a forty-five second deadline and one retry, and the evidence loop has a
forty-second gathering budget after which the tools are withheld so the model must answer from
what it holds. Both exist because one ordinary call once took 609 seconds while every other
call that day took one to nine, whatever its shape. A stalled call is indistinguishable from
the god being down. `MCGOD_MODEL_TIMEOUT` and `MCGOD_ANSWER_BUDGET` tune them. Typical answers
now run 4 to 18 seconds.

## Acting on the world

Three tools, not one. `act_on_world` runs commands. `grant_power` gives abilities no command
can express — flight without creative, a fireball from an empty hand, immunity to your own
fire — held per player with an expiry, restoring what was there before, and needing no client
mod. `design_build` asks a separate build model (`MCGOD_BUILD_MODEL`, currently
`openai/gpt-6-astra`) for the commands that make a shape, because holding a figure in mind is
a different skill from conversation and the dialogue model was visibly bad at it.


Acting is a tool inside the chat loop, alongside rendering and entity inspection, so the god
can look, act, look again and correct before it speaks. A command that reports success but
changes nothing ("Changed 0 blocks") is marked and never counts as done. Every act is recorded
with the position it ran at. The loop is bounded by `MCGOD_ACT_BUDGET` (60s), after which the
tools are withheld and it must answer from what it has done and seen.


The god can run Minecraft commands, in any number and at any rate. `CommandService` in the
plugin decides what runs: an allowlist of twenty-nine commands and a redundant forbidden list
covering op/stop/reload/ban, a refusal of `execute`, a refusal of anything that prints to chat
because speech is budgeted separately, and the game's own 32948-block fill limit. There is no
command budget and no cooldown: how much the god does is a question about what it was asked
for. `agent/commands.py` mirrors those lists so a refusal is immediate and well worded; a test
parses the Java and fails if the two disagree. The agent can permit nothing.

Two capabilities make "anything" true. An **anchor** (a player name) makes the plugin wrap the
command in `execute as X at X run`, so `~ ~10 ~` is ten blocks above that player; the wrapping
is composed by the server and never supplied by the model, which is how `~` works without
`execute` being available. A **spell** is commands plus an interval plus a duration, scheduled
in the plugin so a five-minute effect survives the agent being busy or restarting, and
cancelled when the plugin unloads.

`CommandRunner` drains 200 queued commands per tick. That is the one hard constraint and it is
non-negotiable rule 1, not a limit on what may be asked: the request is unbounded, the pace is
not. `/mcgod stop` cancels every running effect and everything queued, and lives in the plugin
so it does not depend on the agent being reachable.

A one-shot batch replies when it has actually run, carrying each command's own result, so
success is counted from outcomes rather than from acceptance; a spell replies immediately
because it runs for minutes. When every command fails the god withdraws the claim instead of
appending a correction to it, and one corrective attempt is made with the server's own error
in front of the model.

Commands run before the god speaks, and a refusal is admitted in the reply rather than
papered over. If the grounding guard throws the prose away but an act succeeded, the reply is
rebuilt from the server's own words: a refusal must never hide a gift. The command's own output is captured and returned, so the god reports what
happened rather than that dispatch succeeded. Every command is recorded as a `god_command`
event with actor `god`, which is a non-player actor alongside `world`: no player row, no
activity, no region cell.

## Quests

The model proposes natural quest intent and dialogue. Deterministic code accepts only a
validated structured spec, persists one active quest per actor, and uses cheap O(1) watchers for
countable progress. Restarts adopt valid active quests and abandon invalid duplicates.

Hard checks establish facts such as substantive effort and whether work still stands. Semantic
judgment determines whether a result fulfills intent when appearance matters. Rewards remain
in-world. Quest prose should identify places naturally and avoid raw coordinates.

## Model providers and current routing

All production calls go through `agent/model_api.py`. The project uses one Messages-style
internal contract; the adapter handles Anthropic or OpenRouter chat completions, including
images, tools, stop reasons, usage, and Pydantic structured outputs.

Current local OpenRouter routing is:

```dotenv
MCGOD_MODEL_PROVIDER=openrouter
OPENROUTER_API_KEY=...                    # never commit the actual key
MCGOD_OPENROUTER_CLASSIFY_MODEL=openai/gpt-5.6-luna
MCGOD_OPENROUTER_DIALOGUE_MODEL=openai/gpt-5.6-luna
MCGOD_OPENROUTER_VISION_MODEL=google/gemini-3.7-flash
MCGOD_OPENROUTER_REASONING_EFFORT=low
```

Anthropic remains supported and reversible:

```dotenv
MCGOD_MODEL_PROVIDER=anthropic
ANTHROPIC_API_KEY=...
MCGOD_CLASSIFY_MODEL=claude-haiku-4-5
MCGOD_DIALOGUE_MODEL=claude-opus-5
# MCGOD_VISION_MODEL may be separate; otherwise dialogue handles vision.
```

`MCGOD_SEGMENT_MODEL` is a one-run segmentation override for evaluation. Exported variables take
precedence over `agent/.env`. Restart Python after switching providers; Paper need not restart.

The OpenRouter adapter needs the `openai` package. If an older environment raises
`ModuleNotFoundError: openai`, reinstall `agent/requirements.lock` into that environment.

Observed locally, Gemini 3.7 Flash has been the best current cost/latency-quality compromise for
structure images, usually around 10–14 seconds. Luna has been appropriate for cheap dialogue and
structured work, around 15–24 seconds in observed tests. `qwen/qwen3.5-122b-a10b` did not finish
the segmentation comparison in more than two minutes and is not recommended for this loop.
Reevaluate with the corpus rather than selecting from one screenshot.

## Setup and normal operation

Create or refresh the Python environment:

```bash
cd agent
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
cp .env.example .env
```

Configure one provider in `agent/.env`, then start Paper and the agent separately:

```bash
cd server
java -jar paper-26.2.jar --nogui
```

```bash
cd agent
.venv/bin/python god.py
```

To rebuild and deploy the plugin:

```bash
cd plugin
./gradlew deploy
```

Restart the Minecraft server after deploying a plugin jar. Python-only changes normally require
restarting only `god.py`.

If Paper reports `world/session.lock: already locked`, another server process owns the world or
exited abnormally. First find and cleanly stop the existing Java server. Never delete
`session.lock` while a server is running; two writers can corrupt the world.

## Known limitations and next high-value work

1. Expand `segment_truth.json` into a representative cold/warm corpus: both smileys, the golden
   arch inside generated terrain, rails plus stations, dense villages, generated renovations,
   touching-but-distinct builds, small symbols, demolitions, and multi-session edits.
2. Add an in-game player correction/naming interaction with explicit `OBSERVED` provenance.
   Players should be able to teach “this is a smiley” without SQLite edits, while god speech
   remains `ASSERTED` and non-promotable.
3. Add Java behavioral tests for event payloads, queue/dispatcher behavior, container diffs,
   vehicle passenger identity/surface fields, and environment RPC bounds. The plugin currently
   compiles but has no automated Java test sources.
4. Add model-role telemetry: latency, cost, tool rounds, SQL failures, render use, segmentation
   metrics, and grounded-answer quality. Current model choice is partly based on manual runs.
5. Grow capture only where a general missing fact cannot be reconstructed. New events must be
   additive, low-noise, replay-compatible, and tested. Do not capture every click for one story.
6. Improve collaborative authorship. Exact replay establishes who last supplied current blocks,
   but shared construction, ownership language, and transfer need a general policy and fixtures.
7. Continue validating cold discovery. Warm segmentation has prior geometry; cold segmentation
   can still merge a settlement into one object. A second cold sweep should converge without
   inheriting semantic labels.
8. Broaden seed/environment queries carefully. They know selected generator locations and
   biomes, not arbitrary current-world details.
9. Document backup and versioned migration before using the schema on worlds that cannot be
   cheaply replayed. The event corpus is currently the recovery backbone.
10. Quest variety and long-term player collaboration are less mature than memory and structure
    systems. Improve them after world-state and retrieval evaluations are stable.

Small planar symbols are inherently hard for general vision models. The answer is not a smiley
detector: improve views, provide relevant work context, accept trusted player correction, and
measure the entire category.

## Safe development workflow

1. Reproduce from a session, bounded live scan, or explicit database query.
2. Locate the owning layer: capture, history, deterministic index, scan, provenance, evidence
   selection, vision, narration, or render.
3. Change the general contract or invariant at that layer.
4. Add an offline regression or segmentation truth case.
5. Run all 170 Python tests, the plugin build, and render audit.
6. For visual work, open every affected sheet instead of checking filenames alone.
7. Record material decisions and results in a new dated session log.

Do not erase user data or unrelated local changes. Event JSONL is source, not scratch. Render
cleanup should use the archive path. Resolve world locks through processes, not lock deletion.
